title: 我做了一个把视频变成可发布内容的开源工具，想把它认真做成真正可用
---

过去一段时间，我一直在做一个自己会长期使用的开源项目：`video2post`。

它的目标很直接：

把 YouTube、B 站这类视频内容，尽可能顺滑地变成可编辑、可二次创作、可直接发布的文字和素材。

我做这个项目，不是因为“想做一个 AI 项目”，而是因为我自己真的有这个痛点。

我平时会看很多 YouTube 英文技术视频，也会看一些 B 站内容。很多视频本身信息密度很高，但真正麻烦的是后半段：看完之后，如果想把内容整理出来，再做成适合发布的文字稿，整个过程会非常碎，也非常耗时间。

通常你得做这些事：

- 下载或提取音频
- 转写
- 翻译或整理
- 提炼重点
- 改写成适合发布的内容
- 再补一个封面图

如果全靠手工做，这条链路非常重。于是我开始自己搭一套工具，尽量把这件事真正跑通。

## `video2post` 现在已经做到什么程度了

这个项目已经不是停留在想法阶段了，而是已经能真实跑起来，并且我一直在用真实链接做测试。

目前已经做出来的能力大概包括：

- 支持 YouTube / B 站视频链接
- 下载音频并标准化
- 英文 / 中文转写基础链路
- 生成适合 X 发布的内容：
  - `x_article.md`
  - `x_thread.md`
  - `x_titles.md`
- 生成封面图 MVP：
  - `cover.jpg`
  - `cover.meta.json`
- 支持 `retry`、`generate`、`tasks`、`doctor` 这些更接近真实使用的 CLI 能力

换句话说，这个项目已经从“一个想法”进入到了“真的能用，但还没有完全打磨好”的阶段。

## 最近我重点在解决什么问题

最近我专门花了一轮时间调本地 ASR 的体验。

一开始，`faster-whisper` 在我这台 Mac 上的体感并不理想。后来我又接入了 `mlx-whisper` 做真实对比，把同一份音频在不同方案下反复验证。最后项目已经在 macOS 下把默认英文 ASR 切到了更合适的路线，整体体验往前走了一步。

这种优化不会让项目一夜之间变“完美”，但它很重要。

因为一个工具从“能跑”到“愿意每天拿来用”，中间差的往往不是一个大功能，而是很多小问题是不是被认真解决掉了。

## 我现在最关心的，不是功能更多，而是它要真正可用

我不太想把这个项目做成一个“功能很多，但自己都不用”的开源仓库。

我更想把它做成一个创作者自己愿意长期使用的工具。

所以接下来我最关心的方向，反而不是堆更多表面功能，而是继续把这些关键点做稳：

- 长视频分块与分层摘要增强
- `--fast` 快速出稿模式
- B 站中文链路和 `FunASR` 稳定化
- 本地音频 / 视频文件输入
- X 封面图的多候选与智能选帧
- 下载 / ASR / LLM 错误提示与诊断增强
- 更轻量的任务浏览和本地工作台

这些事不一定最“炫”，但它们决定了这个项目会不会从“能跑”真正走到“长期可用”。

## 我想把它开源地认真做下去

如果你刚好对这些方向感兴趣：

- Python / CLI / AI workflow
- ASR / Whisper / FunASR / MLX
- Prompt engineering / 内容生成
- 创作者工具 / 效率工具
- X / 自媒体发布工作流

欢迎一起来参与这个项目。

我已经把后续方向拆成了一组 issue，方便并行推进。你可以提建议、认领 issue、提 PR，或者直接一起讨论产品和技术路线。

我很欢迎这样的协作方式：

不是为了“把一个开源项目做得看起来很大”，而是一起把一个真的有人会长期使用的工具慢慢打磨出来。

## 为什么我觉得这件事值得做

我越来越强烈地感觉到，未来会有越来越多创作者不是缺内容，而是缺一条更顺滑的内容加工链路。

视频里已经有高质量信息，但从“看见内容”到“发布内容”之间，仍然有大量机械、重复、低效的工作。

如果这条链路能被认真做好，创作者能节省下来的，不只是时间，而是更多真正用来思考、判断、表达的精力。

这也是我想持续把 `video2post` 做下去的原因。
